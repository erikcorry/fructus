Proposal for 32 bit Fructus:

All registers 32 bit.
Still only 8 registers, now 1-5 bytes per instruction.

Most insns unchanged.

Extra insns - 3-6 new rows:

ld16 - new name of ld, zero extending.
st16 - new name of st, zero extending.
st - 32 bit store
ld - 32 bit store
bic - lhs & (~rhs), needed because of immbit5 change.
mov #imm32 to set all 32 bits. We should take advantage of variable length and avoid the mov/movhi dance.
Maybe rot for hash functions.

Addressing modes:
imbit5 now just 1 << n, no inverted immediates with mostly 1's, but see bic.
immask5 needs a new set.  We have 32 codes, they don't have to be 16 and their inverses.

push, pop, ldm, stm now are 32 bit

shifts now use low 5 bits to shift.  imm5 covers full range and is interpreted unsigned
due to the truncation.

Long jumps and calls now use 32 bit immediate locations.

Open questions:

  Should branches have 2 bytes of relative indirection?
    Would make them 4 byte instructions.
    A branch over a long jump looks stressful for the branch predictor
  Should we make minimum insn length 2.
    Single byte instructions are not that common and it seems like
    it would make the worst case for a parallel insn decoder simpler.
    Or even more radical, we should abolish 3 byte insns, leaving
    2, 4, 5 only.  See imm10 below.  The other 3 byte insns are
    mov #imm16, which would be replaced with two lines, #imm8 and #imm24.
  Should imm10 (three byte insns) be replaced with imm18 (four byte insns).
    Probably not, +-512 bytes is OK and we would still need r5 and mov #imm32.
  Should we restrict insn sizes to 2, 4, 5

                   r0-19 r0-19           2 bytes, 2 columns
                   r0-19 r0-19 r0-19     3 bytes, 1 column
